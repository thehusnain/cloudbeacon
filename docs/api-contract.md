# Cloud Beacon: API Contract (Agent <-> Backend)

Status: DRAFT v0.1. Needs agreement from both team members.
This file wins over any overview in PROJECT.md. Changes must be agreed by both owners and bump the version.

## 1. Conventions

- Base URL: `https://<backend-host>/api` (HTTPS only in production; `http://localhost:5000/api` in dev)
- Format: JSON, UTF-8, `Content-Type: application/json`
- Timestamps: ISO 8601 in UTC, e.g. `2026-11-02T10:15:00Z`
- IPs: plain string, IPv4 or IPv6
- Agent auth: `Authorization: Bearer <agentToken>` (except `/agent/enroll`)
- Error format (all endpoints):

```json
{ "error": { "code": "INVALID_KEY", "message": "Human readable message" } }
```

| HTTP | Meaning | Agent should |
|---|---|---|
| 200/201 | Success | Continue |
| 400 | Validation error | Fix the payload, do not blindly retry |
| 401 | Bad/revoked agent token | Stop sending, log, require re-enrollment |
| 404 | Server was deleted | Stop and uninstall/idle |
| 429 | Rate limited | Wait for `Retry-After` seconds |
| 5xx / network error | Backend problem | Keep buffering, retry with backoff |

Retry backoff: 5s, 10s, 30s, 60s, then every 60s. Never drop buffered events while retrying.

## 2. Enrollment

`POST /agent/enroll` (no auth, rate limited)

Request:
```json
{
  "key": "one-time-enrollment-key",
  "hostname": "web-server-01",
  "os": "Ubuntu 24.04",
  "ip": "203.0.113.10",
  "agentVersion": "0.1.0"
}
```

Response 201:
```json
{
  "serverId": "665f1c2e9b1e8a0012ab34cd",
  "agentToken": "long-random-secret",
  "heartbeatIntervalSeconds": 30
}
```

Errors: `INVALID_KEY`, `KEY_EXPIRED`, `KEY_ALREADY_USED` (all 400).
The key is valid for 15 minutes and works once. The agent must store `agentToken` securely (file mode 600, root only). The backend stores only its hash and never shows it again.

## 3. Heartbeat

`POST /agent/heartbeat` (agent auth). Sent every 30 seconds. Backend marks the server offline after 90 seconds of silence.

Request:
```json
{
  "timestamp": "2026-11-02T10:15:00Z",
  "agentVersion": "0.1.0",
  "stats": { "cpuPercent": 1.8, "memoryMb": 24, "bufferedEvents": 0 }
}
```

Response 200:
```json
{
  "serverTime": "2026-11-02T10:15:00Z",
  "rulesVersion": 3,
  "commands": [
    {
      "commandId": "665f1d...",
      "type": "block_ip",
      "payload": { "ip": "198.51.100.7", "durationSeconds": 3600 }
    }
  ]
}
```

- If `rulesVersion` differs from what the agent has, it calls `GET /agent/rules`.
- `commands` holds pending commands; the agent executes them and reports results (section 6).

## 4. Events

`POST /agent/events` (agent auth). Sends a batch, max 500 events per request. Used for live events (batch of 1 is fine) and for buffered events after being offline.

Request:
```json
{
  "events": [
    {
      "eventId": "0b7e6f0e-6a53-4d63-9d5a-3a4e2f6c1a11",
      "type": "ssh_failed_login",
      "severity": "medium",
      "sourceIp": "198.51.100.7",
      "timestamp": "2026-11-02T10:14:58Z",
      "details": { "user": "root", "port": 22, "method": "password" }
    }
  ]
}
```

Response 200:
```json
{ "accepted": 1, "duplicates": 0 }
```

Rules:
- `eventId` is a UUID generated by the agent at detection time and kept when buffered. The backend ignores duplicates, so resending is always safe.
- `timestamp` is when the event happened on the server, NOT when it was sent.
- `severity`: `low | medium | high | critical`
- `sourceIp` is optional for events without a remote IP (e.g. file changes).
- Reject the whole request (400) only if the JSON is malformed; invalid single events are reported as `{ "rejected": [{ "eventId": "...", "reason": "..." }] }` in the response and the rest are accepted.

### Event types and `details`

| type | Meaning | details fields |
|---|---|---|
| `ssh_failed_login` | Failed SSH login | `user`, `port`, `method` |
| `ssh_login_success` | Successful SSH login | `user`, `port`, `method` |
| `root_login` | Root logged in | `user`, `method`, `tty` |
| `port_scan` | Port scan detected | `portsScanned`, `windowSeconds`, `scanType` |
| `ping_scan` | Ping sweep/flood detected | `count`, `windowSeconds` |
| `file_modified` | Watched file changed | `path`, `oldHash`, `newHash`, `user` |
| `file_deleted` | Watched file deleted | `path`, `user` |
| `permission_changed` | File permission changed | `path`, `oldMode`, `newMode`, `user` |
| `system_log` | Relevant system log entry | `source`, `message` |
| `ip_blocked` | Agent blocked an IP | `ip`, `reason`, `durationSeconds` |
| `ip_unblocked` | Agent unblocked an IP | `ip` |
| `file_protection_triggered` | Protected file change was blocked/reverted | `path`, `action` |

`details` may contain extra fields; the backend stores them as-is. New event types must be added to this table first.

## 5. Rules

`GET /agent/rules` (agent auth)

Response 200:
```json
{
  "rulesVersion": 3,
  "rules": [
    {
      "ruleId": "665f1e...",
      "name": "SSH brute force",
      "type": "ssh_failed_login",
      "severity": "high",
      "enabled": true,
      "conditions": { "threshold": 5, "windowSeconds": 60, "groupBy": "sourceIp" },
      "action": "block"
    }
  ],
  "protectedPaths": ["/etc/passwd", "/etc/shadow", "/etc/ssh/sshd_config"],
  "allowlistIps": ["10.0.0.0/8"]
}
```

- `action`: `alert` (report only) or `block` (report and block the source IP).
- The agent evaluates rules locally (so it works offline). The backend also evaluates events it receives to create alerts.
- `allowlistIps` must never be blocked.

## 6. Command results

`POST /agent/commands/:commandId/result` (agent auth)

Request:
```json
{ "status": "done", "message": "iptables rule added", "timestamp": "2026-11-02T10:15:05Z" }
```
`status`: `done | failed`. The backend marks the command accordingly. Commands not reported within 5 minutes are re-sent in the next heartbeat.

Command types: `block_ip` (`ip`, `durationSeconds`), `unblock_ip` (`ip`).

## 7. Offline behavior

1. Agent keeps detecting and storing events locally (disk-backed buffer) when requests fail.
2. When the connection returns, it sends buffered events oldest first, in batches of up to 500.
3. A batch is deleted from the buffer only after a 200 response.
4. Heartbeat resumes immediately on reconnect.
